Sliding-Window Streaming VLM Smoke Test — Qwen3.8-27B vs Muse Glimmer 30B

Oct 5, 2026 completed videostreaminginteractionrecurrent memory

Two offline VLMs are run as causal online assistants: they only ever see the 8 most recent frames (1 fps) plus a short memory they wrote themselves on the previous call. Replayed in media time on 5 randomly sampled items from each of five streaming video benchmarks (25 items, 50 trajectories, 5,578 calls). This is a pipeline smoke test, not a benchmark result.

Overview

Question: can an ordinary VLM act as an online assistant when wrapped with a bounded visual window and a recurrent text memory, and does the whole chain — data acquisition, causal decoding, inference, export, scoring — work across benchmarks with very different interaction protocols? Outcome: all 50 model–item trajectories completed with no runtime errors; 8 of 5,578 outputs were malformed JSON. The clips below show what the models saw and said.

Models
Qwen/Qwen3.8-27B @ 1d4bf0f2 (non-thinking) · meta-models/Muse-Glimmer-30B @ a4e59da5 (reasoning_strength = low)
Benchmarks
Ego-MC-Bench · Wearable AI (val) · StreamingBench (visual cohort) · OVO-Bench · ProactiveVideoQA
Sample
5 items per benchmark, uniform without replacement, seed 42 (per-benchmark seed = first 8 bytes of SHA256("42:<benchmark>"))
Hardware
8 × NVIDIA H200, BF16, batch size 1, one model per process; ~3.2 h wall time

Setup

Observations
1 frame per second of permitted media time, long edge ≤ 672 px; identical frame bytes for both models
Window
The 8 most recent permitted frames; at a fractional query time the latest frame at or before it is added; never a future frame, never an unobserved interval
Memory
Model-written JSON (observed_facts, completed_steps, current_state, pending_commitments, uncertainties), bounded to ≤ 512 tokens / 2,048 characters
Cadence
Memory refresh every 2 s; 10 s for media longer than 10 min (declared deviation); benchmark decision times unchanged; StreamingBench proactive polls every 1 s
Decoding
Greedy, ≤ 4,096 new tokens; Muse's to=self channel discarded, only the terminated to=user channel parsed; Qwen enable_thinking=False
Time basis
Media time: a slow call never costs the stream observations or decision opportunities; latency logged separately (Qwen ≈ 11 s, Muse ≈ 16 s per call)
Isolation
Memory resets between items and models; Ego-MC resets at every released instruction; OVO probes at the same timestamp branch from one frozen state
Visibility
Answer keys, gold dialogue and reference times are kept in a private object the prompt builder cannot read
Software
transformers 5.18.0 · torch 2.14.1+cu130 · torchcodec 0.17.0 · flash-linear-attention 0.5.2

Pipeline

  1. Inventory + locks
  2. Normalize annotations
  3. Seeded selection
  4. Acquire selected media
  5. Decode validation
  6. Causal replay
  7. Export
  8. Score

Per call: current media time → standing task text → public dialogue so far → the frame window with timestamps → the previous memory → one call-specific instruction. The model returns one JSON object {"decision": answer|speak|silent, "text": …, "memory": {…}}. A valid reply commits the memory; an invalid one keeps the previous memory and is logged. Every call is checkpointed, so runs resume without duplicating or skipping decision points. Per benchmark: Ego-MC releases each instruction at its timestamp and monitors for Feedback/Success; Wearable EgoProactive scores one decision per chunk end; StreamingBench answers at the question time; OVO dispatches probes in time order; ProactiveVideoQA polls and decides when to speak.

Prompts

System prompt v2, identical for both models
You are an online video assistant watching a live stream. You only ever see the most recent frames of the stream (each labeled with its absolute time in seconds) plus a short written memory that you yourself produced on the previous call. Nothing else about earlier footage survives, so your memory must carry everything you will need later.

Rules:
- Describe only what the frames support. Do not invent events, speech, or future actions.
- Earlier frames are gone; rely on your memory for anything before the current window.
- Keep the memory compact and factual. Hard limits: observed_facts at most 8 entries, completed_steps at most 6, pending_commitments at most 3, uncertainties at most 3; every entry at most 15 words and prefixed with its time (e.g. "12s: ..."); current_state at most 40 words. Merge or drop older entries instead of exceeding these limits. The memory is for YOUR later use, not an answer.
- Reply with ONE JSON object and nothing else, in exactly this shape:
{"decision": "answer" | "speak" | "silent", "text": "<your answer or utterance, or empty string>", "memory": {"observed_facts": [...], "completed_steps": [...], "current_state": "...", "pending_commitments": [...], "uncertainties": [...]}}
- decision must be "answer" when a question is asked of you now, "speak" when you choose to say something proactively, and "silent" otherwise (then text is "").

Show all eight 
refresh:  No response is required at this moment: set decision to "silent" and text to "" and update your memory.

answer_mcq:  A multiple-choice question has just been released (see "Released now"). Answer it now: set decision to "answer" and put ONLY the letter of your chosen option (A, B, C or D) in text.

answer_free (Wearable EgoConv):  The user has just asked you the question shown under "Released now". Answer it now in one to three sentences based on what you have seen: set decision to "answer".

probe_crr (OVO):  Decide whether the visual content you have seen so far, especially the latest frames, provides enough information to answer the standing question. Set decision to "answer" and text to exactly "Yes" or "No".

interval_end (Wearable EgoProactive):  A video chunk has just ended. Decide whether to interrupt the user now with the next useful step-by-step guidance or correction for their standing request: set decision to "speak" with the utterance, or "silent" if nothing should be said yet. Do not repeat guidance you already gave.

monitor (Ego-MC):  You are guiding the user through the CURRENT recipe step (the standing instruction). If the latest frames show the user making a mistake relative to that step, set decision to "speak" and text to "Feedback: <short correction>". If the step now appears completed, set decision to "speak" and text to "Success: <short confirmation>". Otherwise set decision to "silent". Do not repeat feedback you already gave.

proactive poll (StreamingBench):  The standing request asks you to output a specific phrase as soon as a condition becomes true. If the condition is true in the latest frames, set decision to "speak" and put exactly the requested output in text; otherwise set decision to "silent".

proactive poll (ProactiveVideoQA):  You are a proactive assistant answering the user's standing question as the video unfolds. If the latest frames show something new that answers or advances the question, set decision to "speak" with a concise reply; otherwise "silent". Never repeat an earlier reply.
