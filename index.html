Sliding-Window Streaming VLMs: Full Evaluation on Ego-MC-Bench and Wearable AI

Oct 12, 2026 completed videostreaminginteractionrecurrent memorylatency

Qwen3.8-27B and Muse Glimmer 30B run as causal online assistants (an 8-frame sliding window plus a memory they write themselves, replayed in media time) on the Wearable AI validation split (all 2,100 sessions, with the official starter-kit protocol and, for EgoProactive, also the Pro2Bench paper protocol) and on Ego-MC-Bench (39 videos) under the Ego-MC-Bench paper's own evaluation protocol and official evaluator. Only the model's view (window plus memory) differs from each benchmark's protocol. An isolated latency study compares both models with and without reasoning.

OverviewEgo-MC-BenchWearable AI

Overview

  • Question. How well does an offline VLM work as an online assistant when it only sees the 8 most recent frames and a short self-written memory, and what does each call cost in latency?
  • Scope. 2 models on all items: 2,100 Wearable AI sessions (700 each for EgoLongQA, EgoConv, EgoProactive; 138,898 calls per model) with the official starter-kit protocol, EgoProactive again with the Pro2Bench paper protocol (700 sessions, 46,832 calls per model), and 39 Ego-MC videos in both of the paper's settings, per-recipe step and full recipe (13,160–18,329 calls per model and setting).
  • Outcome. Every item ran to the end for both models. On Wearable AI, 101 (Qwen) and 323 (Muse) of 138,898 calls gave no usable output; on Ego-MC, Muse parsed on every decision prompt and Qwen on 99.5 %. The EgoConv LLM judge is still queued.
  • Takeaway. The two models fail in opposite ways, and the prompt decides which way. On Ego-MC, Muse catches mistakes best (F1 0.28–0.29, above every model in the paper) but rarely confirms a step is done; Qwen confirms steps well (IC-Acc 40–44) but almost never flags a mistake. On Wearable AI with the official prompts Qwen leads on EgoLongQA (0.66 vs 0.52) and on EgoProactive (macro F1 0.49 vs 0.36, Muse interrupts in 98 % of chunks), but with the Pro2Bench paper prompt Muse reaches G-mean F1 0.53, close to the paper's best zero-shot 0.57, while Qwen almost never speaks (0.26). Neither fits the leaderboard's 300 s per-sample budget inside this wrapper; Muse loses almost everything under it.

Shared Setup

Models

  • Models. Qwen3.8-27B (non-thinking mode, greedy decoding) and Muse Glimmer 30B (reasoning_strength = low, the model's official sampling: temperature 1.0, top-p 0.95, top-k 64, seeded per call; only the to=user channel is parsed). On the Pro2Bench protocol both are greedy, as in the paper. BF16, pinned revisions.

Streaming wrapper

  • Window. The video is replayed in media time at one frame per second. Each call sees only the 8 most recent frames (long edge ≤ 672 px): never a future frame, never an unobserved interval.
  • Memory. A small JSON object (facts, completed steps, state, commitments, uncertainties) that the model rewrites on every call, bounded to 512 tokens. It is the only state that survives beyond the window.

Serving and compute

  • Backend. vLLM (the official Muse Glimmer image for both models), one server per GPU, 92 % of GPU memory for weights and KV cache. Calls inside one item stay sequential (each depends on the previous memory); throughput comes from running 40–64 items at once per GPU.
  • Hardware. UW Hyak Klone, mostly preemptible H200 (141 GB) plus A100 80 GB. Items are pulled from a shared queue, so preempted jobs lose no work.
  • Differences from the earlier smoke test. All items instead of 5 per benchmark, only these two benchmarks, vLLM instead of transformers, Muse sampled as its documentation requires, and both benchmarks rerun with their official protocols (Ego-MC paper protocol and QICD evaluator; Wearable AI starter kit and Pro2Bench).

Benchmark-specific data, protocols and prompts are on the Ego-MC-Bench and Wearable AI pages.

Pipeline

Eight stages, from pinned sources to scored predictions. Everything before replay is deterministic and frozen before any model runs.

One replay step at media time t: the model gets only what is public by t plus its own memory. At a decision point it answers the benchmark's official prompt; a separate call then rewrites the memory.

  • Causal by construction. Frames are fetched by presentation time (never after t, never from unobserved intervals); questions, steps and probes are released only at their annotated times.
  • Memory is the only long-term state. It is rewritten by the model every call and bounded deterministically; it resets per item and per model, and at every Ego-MC instruction.
  • Gold stays private. Answer keys, reference replies and their timestamps are read by the exporter and scorer only.
  • Resumable. State is checkpointed after every call; preempted GPU jobs are requeued and any worker resumes an abandoned item from its last completed call.

Latency

Isolated study: one vLLM server on one H200, one stream at a time (no batching or queueing), the same 20 items for every configuration (5 per Wearable AI subtask and Ego-MC, first 30 calls each, Wearable AI prompts). The server's first, cold call is excluded. "First answer token" is when the user-visible answer starts: after Muse's to=self reasoning, after Qwen's </think>.

  • Reasoning, not the model, sets the latency. Prefill and decode speed are almost the same for both models. Muse always reasons in its to=self channel (its template has no off switch), so against non-reasoning Qwen it is 1.9× slower end to end and its answer starts about 3.3 s later. With Qwen's thinking turned on, Qwen reasons 3.5× longer than Muse (699 vs 202 tokens) and its answer starts about 3× later (10.9 s vs 3.7 s).
  • The chart shows end-to-end latency for the default configurations (Qwen thinking off, Muse reasoning low) per subtask.
  • Under load. During the full run, with 40–64 concurrent streams per GPU, median call latency rose to 10.2 s (Qwen) and 16.9 s (Muse) on Ego-MC and to 24.6 s and 38.6 s on Wearable AI. These numbers measure throughput settings, not the model.
  • Real time. Neither configuration keeps up with a 2 s refresh cadence on one H200 even in isolation. On Ego-MC, one 5 s turn takes up to three sequential calls. Latency here is measured under media-time replay, where the stream waits for the model. Only latency was measured for Qwen with thinking on; its benchmark accuracy is not known yet.

Observations and Conclusion

  • The two models sit at opposite operating points. On Ego-MC, Muse flags mistakes often: recall 0.30–0.35 and precision 0.23–0.28, the highest F1 (0.28–0.29) of any model including the paper's, but it confirms few steps (about 160 "Success" messages vs Qwen's 380), so IC-Acc is 16–18. Qwen confirms steps as well as the paper's Qwen3.5-27B (IC-Acc 44.4 vs 45.5) but flags only about 6 % of mistakes. On EgoProactive the operating point depends on the prompt: with the starter-kit prompt Muse interrupts in 98 % of chunks (silent recall 0.02) and Qwen is balanced (0.40 / 0.59); with the Pro2Bench prompt Muse is the balanced one (0.76 / 0.35) and Qwen almost never speaks (interrupt recall 0.06).
  • Reasoning costs time. Muse's reasoning delays its answer by about 3 s per call; Qwen's thinking mode delays it by about 10 s. Whether that time buys accuracy is untested for Qwen.
  • Conclusion. With a sliding window and self-written memory, both models run end to end on full benchmarks under each benchmark's own protocol, match or exceed the zero-shot results of the Ego-MC-Bench paper, and Muse comes close to the best zero-shot Pro2Bench result, but neither is a usable proactive assistant yet: each is strong on one half of the task (Muse catching mistakes, Qwen confirming progress) and per-call latency is well above the refresh cadence. The results describe these models inside this wrapper and configuration, not the models in general.

Next steps

  • Repeat Muse with several seeds and with greedy decoding, to measure how much sampling moves the scores (39 Ego-MC videos is a small set).
  • Run Qwen with thinking on through the full benchmarks, to pair its latency with accuracy.
  • Run the paper's whole-video setting on the same two models, to separate the effect of the window and memory from the effect of the model.
  • Reword Ego-MC step-completion questions to see whether Muse's low IC-Acc is the prompt or the model.
  • Score EgoConv with the LLM judge (jobs queued) and compute Pro2Bench PQS with an LLM judge (inputs already exported).
  • Cut per-sample cost to fit the 300 s rule: sparser memory refresh, and per-call text after the frames so consecutive calls share a cached prefix.

Reproduction

Code: jxb1st/glimmer_qwen_streaming_baseline-code, config configs/full_klone.yaml. On a SLURM cluster with the vLLM Muse Glimmer image:

scripts/download_all.sh all                                    # pinned models + full benchmark data
python -m streaming_smoke {inventory,sample,acquire,validate,estimate} --config configs/full_klone.yaml
scripts/serve_and_run.sh muse30b 1 64                          # one worker per GPU; start as many as available
scripts/serve_and_run.sh qwen27b 1 64
python -m streaming_smoke score  --config configs/full_klone.yaml
python -m streaming_smoke report --config configs/full_klone.yaml
scripts/latency_study.sh muse30b 5 30                          # isolated single-stream latency
scripts/latency_study.sh qwen27b 5 30
scripts/latency_study.sh qwen27b 5 30 configs/full_klone_qwen_thinking.yaml
