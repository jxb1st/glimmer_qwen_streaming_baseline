Sliding-Window Streaming VLM Smoke Test — Qwen3.8-27B vs Muse Glimmer 30B

Oct 5, 2026 completed videostreaminginteractionrecurrent memory

Two ordinary offline VLMs are turned into online assistants with a causal 8-frame sliding visual window plus a self-generated recurrent text memory, then replayed in media time on five randomly sampled items from each of five streaming video benchmarks (Ego-MC-Bench, Wearable AI, StreamingBench, OVO-Bench, ProactiveVideoQA). All 50 model–item trajectories ran end to end (5,578 calls, 8 unparseable outputs); official or adapted scorers ran where no LLM judge is required. Five items per benchmark establish that the pipeline works; they are not a model ranking.

Overview

The goal was infrastructural: verify that dataset acquisition, causal video decoding, sliding-window inference with recurrent memory, benchmark-format export and the available scorers work together for two 27–30B vision-language models, and report the first numbers on a fixed, reproducible sample. Everything below was produced by one code base (streaming_smoke) with pinned model revisions, pinned dataset revisions and a frozen manifest.

Models
Qwen/Qwen3.8-27B @ 1d4bf0f2 (non-thinking mode) · meta-models/Muse-Glimmer-30B @ a4e59da5 (reasoning_strength=low)
Benchmarks
Ego-MC-Bench (40 videos), Wearable AI val (3 × 700 rows), StreamingBench visual cohort (2,800 items), OVO-Bench (1,640 records), ProactiveVideoQA (1,427 question ids)
Sample
5 items per benchmark, uniform without replacement, seed 42 → per-benchmark seed = first 8 bytes of SHA256("42:<benchmark>")
Hardware
NVIDIA H200 (143 GB), BF16, batch size 1, one model per process; 8 GPUs in parallel (3 Qwen shards, 5 Muse shards), ~3.2 h wall time
Software
transformers 5.18.0, torch 2.14.1+cu130, torchcodec 0.17.0, flash-linear-attention 0.5.2

Research Question

Can an offline VLM act as a causal online assistant when it only ever sees the eight most recent frames and a short memory it wrote itself — and does the whole chain (data → decoding → inference → export → scoring) hold up across five benchmarks with different interaction protocols?

Experimental Setup

Observations
1 frame per second of permitted media time; long edge capped at 672 px, no upscaling; both models receive the same frame bytes and timestamps
Visual window
At most the 8 most recent permitted observations; at a fractional query time the latest frame at or before that time is included; frames never come from the future or from unobserved intervals
Memory
Model-generated JSON (observed_facts, completed_steps, current_state, pending_commitments, uncertainties); bounded deterministically to ≤ 512 tokens / 2,048 characters by pruning oldest entries
Cadence
Memory refresh every 2 s; 10 s for items whose media exceeds 10 min (declared deviation, 9 of 25 items); benchmark-defined question, interval-end and probe times are unchanged; StreamingBench proactive polls every 1 s
Decoding
Greedy, max 4,096 new tokens; Muse to=self reasoning stripped, only the terminated to=user channel is parsed; Qwen enable_thinking=False
Time basis
Media time; a slow call never reduces the observations or decision opportunities of the next one; latency is recorded separately
Isolation
Memory resets between items and models; Ego-MC additionally resets at every released instruction; OVO probes at the same timestamp are answered from one frozen state and their memory changes are discarded
Visibility
Answer keys, gold dialogue and reference timestamps live in a private reference object the prompt builder cannot read; the only teacher-forcing exception (StreamingBench SQA official history) was not exercised because no SQA item was sampled

Per-benchmark adapters

  • Ego-MC-Bench (one annotated video per item, adapted per-recipe-step protocol): each Instruction is released at its timestamp as public task text and resets window + memory; user comments/questions are public; Feedback/Success are private targets. Monitoring polls at the memory cadence until the model's first Success in a step.
  • Wearable AI (one validation row): EgoLongQA streams the whole clip and reveals the MCQ at the end (wrapper convention); EgoConv honours video_intervals and answers at each question turn with its own prior answers as history; EgoProactive makes the query public at the first interval and scores one $silent$ / $interrupt$ decision per interval end.
  • StreamingBench (one real-time question, SQA group or proactive request): stream the permitted prefix and answer at the question timestamp; audio-required Omni-Source items (1,000) excluded from the population.
  • OVO-Bench (one record with all probes): MCQ at realtime for backward/real-time tasks; CRR question public at ask_time with Yes/No probes; SSR/REC queries revealed at probe time; probes dispatched in timestamp order with original indices preserved.
  • ProactiveVideoQA (one question id): user turns and TV subtitles revealed at their annotated times; the model polls at the cadence from the first turn to the media end and decides when to speak; exported as model_response_list.

Method / Pipeline

  1. Inventory + locks
  2. Normalize annotations, quarantine
  3. Seeded selection
  4. Acquire selected media
  5. Decode validation
  6. Causal replay per item
  7. Export
  8. Score

Each call receives: the current media time, the standing task text, the public dialogue so far (new lines marked), the frame window with absolute timestamps, the previous memory, and one instruction for this call. It must return one JSON object {"decision": answer|speak|silent, "text": ..., "memory": {...}}. A valid response updates the memory; an invalid one keeps the previous memory and is logged as a failed call. Every call is checkpointed, so runs resume exactly without duplicating or skipping decision points.

Quarantined before sampling (structural validation only): Ego-MC 1/40 (video starts without an instruction), Wearable 44/2100 (22 dialog turns going backward in time, 21 question/turn mismatches, 1 bad interval), StreamingBench 1/2800 (the sample_7 SQA episode whose last turn precedes the previous one).

Prompts

System prompt prompt_version v2, identical for both models
You are an online video assistant watching a live stream. You only ever see the most recent frames of the stream (each labeled with its absolute time in seconds) plus a short written memory that you yourself produced on the previous call. Nothing else about earlier footage survives, so your memory must carry everything you will need later.

Rules:
- Describe only what the frames support. Do not invent events, speech, or future actions.
- Earlier frames are gone; rely on your memory for anything before the current window.
- Keep the memory compact and factual. Hard limits: observed_facts at most 8 entries, completed_steps at most 6, pending_commitments at most 3, uncertainties at most 3; every entry at most 15 words and prefixed with its time (e.g. "12s: ..."); current_state at most 40 words. Merge or drop older entries instead of exceeding these limits. The memory is for YOUR later use, not an answer.
- Reply with ONE JSON object and nothing else, in exactly this shape:
{"decision": "answer" | "speak" | "silent", "text": "<your answer or utterance, or empty string>", "memory": {"observed_facts": [...], "completed_steps": [...], "current_state": "...", "pending_commitments": [...], "uncertainties": [...]}}
- decision must be "answer" when a question is asked of you now, "speak" when you choose to say something proactively, and "silent" otherwise (then text is "").

Success Cases

OVO CRR, MovieNet tt0080761 (both models 5/5)

Question released at 397 s; probes at 397, 412 (not yet answerable) and 430, 438, 458 s (answerable). Both models said No, No, Yes, Yes, Yes — the memory carried the question across 60 s of 10-s refreshes.

StreamingBench text-rich and object questions

sample_424 “What text is displayed on the screen right now?” and sample_306 “primary color of the subway train” were answered correctly by both models from the current window alone.

Output contract

5,570 of 5,578 calls returned the required JSON; memory pruning was never needed after prompt v2 (no call exceeded the 512-token bound).

Failure Cases

Mistake detection on Ego-MC

Qwen: 1 Feedback in 5 videos (recall 0). Muse: 90 false positives, mostly repeated every poll. The 2-s/10-s monitoring cadence with an 8-frame window gives neither model a stable notion of “already said”.

Same wrong answer on sample_484

Both models answered C (purple, blue) to the racecar order question whose gold is A (red, blue); the sequence had to be reconstructed from memory across several minutes.

JSON formatting slips

8 outputs (5 Qwen, 3 Muse) closed a memory list with an extra ]; they are counted as failed calls, the previous memory was kept, and the trajectory is flagged.

Observations

  • The external adaptation works mechanically for both models: no run-time errors, 50/50 trajectories complete, resume and sharding behaved.
  • Behavioural styles differ sharply: Qwen is conservative (few proactive utterances, no false corrections, misses all mistakes); Muse is talkative (more interventions, higher recall, many repeats).
  • Per-call cost is dominated by generated tokens, not frames: prompt v2 cut Qwen from 26 s to ~11 s per call; Muse's low-effort reasoning channel still adds ~5 s.
  • Long items (9 of 25 exceed 10 min) ran at the 10-s cadence; this changes the memory trajectory and must be stated whenever these numbers are compared.
  • Five uniformly sampled items leave StreamingBench SQA/proactive and OVO REC/SSR unrepresented; the adapters and fixtures for them exist but were not scored.

Conclusion

Every model–benchmark pipeline ran end to end and produced exportable predictions; judge-free scores exist for four benchmarks and PAUC-ready exports for the fifth. On this sample the sliding-window + memory wrapper turns both models into functioning but weak online assistants: competent at window-local questions, unreliable at timing proactive interventions, and prone to either silence (Qwen) or repetition (Muse). The numbers are smoke-test evidence, not a comparison of the two models.

Next Steps

  • Verify the adapted Ego-MC evaluator against the authors' Ego-MC binding before any larger run.
  • Obtain judge access (gpt-4.1 for PAUC; Llama-4-Maverick or an approved alternative for ConvQA).
  • Stratify or enlarge the sample so SQA, proactive, REC and SSR are represented.
  • Add a “what I already said” field or dedup rule to the memory contract to curb Muse's repeated feedback; consider constrained JSON decoding to remove the 0.14 % formatting failures.
  • Run the 2-s cadence on the long items as an ablation of the declared 10-s deviation.
